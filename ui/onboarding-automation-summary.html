What we built for Fyralis onboarding

The onboarding flow now starts in the hosted Fyralis portal, moves into the customer cloud for setup, and uses a local agent CLI to automate BYOC readiness, setup artifacts, and source connection receipts without exporting source secrets or raw customer data.

Current capability

Prototype completeness 92%

Hosted portal captures safe commercial and customer metadata.

Customer-cloud CLI generates setup, plan, validation, and readiness artifacts.

Provider executor can now render or run CloudFormation and Helm with explicit approval.

Onboarding Flow

The product flow is split between the Fyralis-hosted portal and the customer-cloud console. The hosted side never asks for source tokens, cloud secrets, raw logs, prompts, embeddings, or customer payloads.

Host -> Customer Cloud
1 Get Fyralis

Customer chooses Design Partner BYOC or Enterprise.

2 Customer Intake

Company, target cloud, and setup owner are captured.

3 Agent Setup

Fyralis generates BYOC setup artifacts and autopilot commands.

4 Source Autopilot

Every source can be prepared from local customer-cloud refs.

5 Launch

Readiness, first-sync, health, and activation receipts are produced.

Automation Commands

These are the main commands the customer-cloud console or setup owner can run. Individual manual commands still exist as an advanced fallback.

Generate zero-spend local rehearsal

fyralis byoc agent local-rehearsal --region us-east-1 --workdir .fyralis/local-rehearsal --json

Setup Fyralis in customer cloud

fyralis byoc agent autopilot --cloud aws --region us-east-1 --external-id fyralis-acme-finance-pilot --bundle fyralis-byoc-acme-finance.zip --capabilities kubernetes,network,secrets,postgres,s3,kafka --auto-approve --run-readonly-api-probes --run-provider-executor --stack-name fyralis-byoc-acme-finance --json

Execute AWS resources and Helm install

fyralis byoc agent provider-executor --cloud aws --region us-east-1 --stack-name fyralis-byoc-acme-finance --create-change-set --execute-change-set --execute-helm --confirm-cost-and-mutation --json

Discover source gates

fyralis byoc source discover --source all --scopes auto --provider-authorization-mode preauthorized-ref --preauthorized-ref-manifest ./customer-source-refs.json --json

Plan source setup

fyralis byoc source plan --source all --scopes auto --sync-mode dry-run --backfill-window 30d --provider-authorization-mode preauthorized-ref --preauthorized-ref-manifest ./customer-source-refs.json --json

Apply approved source plan

fyralis byoc source apply --source all --requires-approval --plan latest --sync-mode dry-run --backfill-window 30d --provider-authorization-mode preauthorized-ref --preauthorized-ref-manifest ./customer-source-refs.json --json

Validate and activate sources

fyralis byoc source validate --source all --provider-authorization-mode preauthorized-ref --preauthorized-ref-manifest ./customer-source-refs.json --json fyralis byoc source activate --source all --requires-approval --start-first-sync --sync-mode limited-backfill --backfill-window 30d --provider-authorization-mode preauthorized-ref --preauthorized-ref-manifest ./customer-source-refs.json --json

What The CLI Produces

The CLI writes local customer-cloud artifacts. These are safe, structured receipts and manifests, not source secrets.

Area Generated artifacts Purpose
BYOC agent Role template, registration, preflight report, discovery plan, review bundle, apply receipt, CloudFormation template, Helm values, provider executor report, readiness report Prepare and validate the customer-cloud deployment path.
Local rehearsal Local Helm chart, kind runbook, generated Helm values, customer-source refs example Run a zero-spend BYOC rehearsal before touching AWS.
Source setup Discovery, source contract, setup plan, provider setup, secret refs, connection contract, validation, scope receipt, first-sync receipt, activation, readiness receipt Automate every local step and expose only the exact human gates that provider APIs cannot complete.
Status handoff Sanitized readiness and issue-code style receipts Let Fyralis know setup status without receiving raw customer data.

Host vs Customer Cloud Split

This split is the core of the BYOC model.

Fyralis hosted portal Customer cloud console / agent
Plan selection, design-partner intent, customer intake, setup package overview Cloud setup, source credentials, provider sessions, runtime validation, source sync
Stores sanitized onboarding metadata only Stores provider tokens, source refs, raw payloads, logs, prompts, and embeddings
Receives readiness status and bounded issue codes Runs autopilot commands and produces local receipts

Current Honest Status

The onboarding prototype is much closer to the real product flow. The remaining limits are now about customer authorization, provider access, quotas, and live-environment approval.

Done

Customer-cloud executor

The CLI renders CloudFormation and Helm artifacts, can create or execute CloudFormation change sets, and can run Helm install after explicit customer confirmation.

Done

Local BYOC rehearsal

The local chart gives us a no-AWS path to rehearse the gateway, migrations, Kafka topics, object storage, source refs, and workers.

Requires customer refs

Provider authorization

OAuth consent, API-token creation, admin approval, and gateway session authorization can be automated after the customer provides preauthorized refs inside their own cloud.

Live AWS mutations are still outside the zero-spend path. The real execution path is guarded by --confirm-cost-and-mutation and uses customer-local AWS credentials, kubeconfig, and source secret refs.
