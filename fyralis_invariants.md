Here are a few things about Fyralis that must be true at all times:
Each model should be truly atomic and falsifiable. Even a composite model is also atomic because it’s revealing an atomic and falsifiable truth about a group of models.
Each edge between models should be as specific as possible. The system should penalize the use of generic edge types. This is because an edge is another information dimension for the system and using very specific edges help increase its usefulness to the system overall.
A model can be connected to as many other models as needed. It need not be capped. Because any good relation across more models makes the system more valuable.
If a relation between models can not be defined properly by the existing set of edge types, the system should be able to propose a new edge type.
If an edge seems to connect multiple models together, there’s a latent composite model between these models. This means the system should define this composite model and connect multiple models together via the composite model. So we get the benefits of a hypergraph without its complexities.
The system should focus on universally true objects about companies. For example, employees, customers, recurring events in the company, etc. The system should model these objects as richly as possible. So things like patterns, analysis, etc. should be present about these things. These are all still models (which then are projected in the projection layer for better access), but the system should always actively try to map these objects as richly as possible.
The system should not only look at the signals present, but also think about the signals absent. Like a dark matter model. Many signals may not exist in the digital realm coverable by the system. Therefore, if the system sees any anomaly in new signals and what that means for the company’s state based on what the state currently is, the system should infer that there were signals not covered by the system and hence fill that void by proposing dark matter models. The system should then also ask the most relevant person about whether this dark matter model is true or not. If not, ask them to clarify this anomaly the system saw.
The system should be intelligent, adaptive, and always forward looking. For this, the system should take every possible signal, both directly from the ingestion layer, but also based on the internal representations across multiple abstraction layers. For example, a repeated action leads to a pattern and that pattern reveals something about the company’s state.
The system should look for signals in every possible dimension. For example, the history of a model is valuable, the history of how the models have been rearranged is valuable, how two unrelated things might connect to each other, etc. The system should find ways to extract as much value from the existing information we have about the company.
SAGE should turn into a small, adaptive, and powerful company specific model. It understands the company’s core in depth. It’s like a reflex system of the company. It should help guide retrieval and other parts of the system in order to reduce cost and latency while improving the quality of the system. This is especially useful as the volume of signals and models increase. SAGE should also inform how the models should be organized, how the models should be connected to each other, in order to make retrieval easier. Because at the end, the organization of models and their connections should optimize for information value density and how easy it is to retrieve relevant models. This means, SAGE could even propose a custom pathway for retrieval that’s specific to a company itself based on its patterns.
Each Think process should rely as little as possible on the LLM’s power. Because of how well we set up the system around it, we should be able to use cheaper LLMs for a majority of the tasks without any hiccups in the quality of output. If this isn’t true, then there’s a gap in how our system is designed. A well designed system should make LLM’s power less relevant in most cases. It should be absolutely needed only in very powerful tasks. A good retrieval engine is a necessity for this.
The overall system should be as parallelized as possible across all components and data flow in order to reduce latency. Sequential computation only when parallelization is impossible. The system should aim to reduce the latency bottlenecks.
The system should have a stable range of active models at a given time depending on the volume of observations. For example, there should be a point where the historical observations matter less, because most of it is modelled closely by models and edges. So just the current volume of observations/signals should affect most of the additions and edits in the models and edges.in
The system shouldn’t be conservative on creating or editing models. Being more aggressive is better than being more conservative because it helps the company’s state stay up to date. Ideally, every batch should either create new models or at least edit existing ones. But the system should detect that there’s an anomaly if only one of these two is happening very dominantly. For example, if the system only creates new models or only updates existing models, then the system isn’t working as intended.
Any component that exists in the hot path that isn’t absolutely needed for the current process should be processed asynchronously in the background. For example, T4 is a background process that shouldn’t affect the T1 process.
Retrieval latency should be highly optimized to its theoretical limits, especially for T1 and Ask Fyralis primitive. Ignore the LLM level latency, our focus is to bring the non LLM latency as close to zero as possible.
The adaptive inquiry is a very powerful idea for retrieval. Make sure the component is designed to reach its full potential.
The conversation in Ask Fyralis should also be valuable signals for the system to understand what matters for the user and how the user thinks. It should also understand the blind spot of the user (which should make the models about this user richer) and help navigate the conversation accordingly.
The whole system should be as simple as possible without reducing the quality of the system. Any unnecessary component should either be deleted or merged with other relevant components.
To understand whether the system is in its most simplified form or whether a component is borderline unnecessary or redundant, we need to monitor every possible detail about each component and data flow. We can understand the system’s efficiency by analyzing this data. So make sure to implement a system to monitor every possible detail.
The system should be very curious, forward looking, always ask a lot of questions (mostly to itself, but also to its users if needed) to satisfy its curiosity. These questions should be directed towards finding holes in its understanding of the company and things around it. As a result, it should always try to find connections and patterns across seemingly unrelated things. That is one of the core values of the system.
Model layer should be the complex company mapping structure of the system. It is the core of the system. Like a brain of the company. The projection layer on top is an opinionated view of this complex structure so that specific views on this data can be accessed easily.
Fyralis should reliably understand patterns in the actions and data. Then it should make that pattern visible. This newly understood pattern should lead to downstream effects like maybe this changes some commitments or makes something more urgent, etc. Because patterns sit at the highest level of abstraction and changes in such objects likely leads to higher order cascades.
